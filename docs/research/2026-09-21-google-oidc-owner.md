# Google OIDC for one Mentat owner

Research for [Specify Google OIDC owner enrollment, sessions, and recovery](https://github.com/hazeion/agent-os/issues/236), 2026-09-21. This is an implementation proposal, not an assertion that remote authentication is available. No production account, credential, listener, or authentication state was changed during research.

## Decision and evidence

Use a fixed Google OpenID Connect authorization-code flow, executed by Python, to authenticate one explicitly enrolled owner. Issue Mentat's own opaque session afterward. Keep Calendar and other integration authorization separate. The operator supplies their own Google web application client and canonical HTTPS origin through guided CLI configuration. Ordinary browsers need no Mentat passkey enrollment.

Google documents server-side code exchange, exact registered callback matching, nonce handling, and stable `sub` identity; email is mutable and must not identify an owner. Its discovery document currently advertises RS256 and PKCE S256. Select only that fixed issuer and algorithm, not configurable provider URLs. [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect), [live discovery](https://accounts.google.com/.well-known/openid-configuration).

OAuth security guidance recommends PKCE for confidential clients and binding each transaction to the initiating user agent. It discourages implicit tokens in authorization responses. Use S256, state, and nonce together; never downgrade after an error. [RFC 9700, sections 2.1 and 4.7](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1).

The protocol verifier must validate signature, issuer, audience, authorized party where relevant, expiry and nonce before establishing identity. Require an exact single configured audience for this first implementation; reject unsupported multi-audience tokens rather than inventing hybrid-client support. [OIDC Core ID-token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation).

The remainder of this document states proposed Mentat-specific controls and acceptance criteria; these are design recommendations, not claims that Google supplies those controls.

## What the implementation already owns

- [owner_auth.py](../../owner_auth.py) owns transaction-bound authentication, digest-only session/CSRF secrets, revocation, admission budgets, SSE reservations, audit retention and restore sanitization. Existing defaults are 60-minute idle and 24-hour absolute session expiry; 32 owner sessions, eight per credential, 128 terminal sessions with 24-hour grace; 32 pending ceremonies with five unauthenticated; 512 audit rows; two SSE streams per session. Authentication starts are limited to ten per minute, recovery submissions to five, unsafe requests to 60, and security management to one, through its admission scopes.
- [mentat_db.py](../../mentat_db.py) schema 24 hard-couples sessions to a WebAuthn credential through non-null `device_id`. Credentials require COSE keys and disallow backup-eligible passkeys. `authenticate_session` explicitly checks that credential. Google sessions cannot be inserted into this graph unchanged, and fake credential rows would violate its meaning.
- [gateway-authority.ts](../../web/src/lib/gateway-authority.ts) allows local mode only, rejects cross-site metadata, and owns all route admission. The [route manifest](../../web/src/lib/gateway-route-manifest.ts) already distinguishes anonymous authentication, owner sessions, reauthentication and local-only operations. These labels are not a completed remote profile.
- [ARCHITECTURE.md](../../ARCHITECTURE.md) preserves Python authority and loopback operation. Its disabled Caddy profile fixes the Node upstream and tests forwarding-header replacement. [IMPLEMENTATION_PLAN.md](../../IMPLEMENTATION_PLAN.md) records completion through MDA-4C and the current owner-workflow sequence.
- [data_backup_restore.py](../../data_backup_restore.py) calls owner-auth sanitization for restore. Current sanitization preserves credentials/recovery codes but revokes sessions, cancels ceremonies, removes SSE leases and records notices. The new schema must extend that behavior rather than copying live grants.

## Bounded authority and migration

Introduce an explicit singleton owner authentication method, configuration revision and owner generation, plus a bounded Google principal record. Store the normalized Google issuer and exact verified subject in private SQLite. The principal is private account identity, never an Agent/runtime identity or browser-visible ID. Keep only minimal configuration: fixed provider kind, client ID, canonical origin and credential-source kind; the client secret stays in operator-managed private configuration/environment, outside SQLite, backup, Node, agent environments and logs.

Separate authentication principals from session presentation. Rebuild the session relation deliberately so a session binds to the current owner generation and permitted authentication method; retain a nullable legacy credential reference only for genuine passkey sessions. A browser session is not a hardware device. In Google mode, expose session list/revoke controls instead of claiming device-bound credentials. Do not create a new durable browser-tracking identifier merely to reproduce the old eight-per-credential quota. Retain the stronger overall ceiling of 32, and explicitly document the retired credential-scoped quota for Google sessions.

Schema migration alone must neither enable Google nor enroll an owner. Existing roots retain passkey mode until an exact CLI conversion is confirmed. Conversion binds the verified new principal, changes the method and generation, invalidates all sessions and pending transactions, disables legacy credential login and rotates recovery material atomically. Preserve historical credentials as private disabled evidence within existing bounds; do not retain an undocumented second login path. A failed conversion leaves the old method operational. Use the established private mutation lock and backup validation; no in-place downgrade.

Backup validation must know the exact new table/index/trigger graph, singleton constraints, size and row ceilings. Filter disposable OIDC attempts and secrets out of exported snapshots. Restore preserves the snapshot owner binding but invalidates sessions/attempts and disables remote activation until the host administrator reconciles origin, Google client configuration and credentials. Warn explicitly that restoring an old snapshot can restore an earlier owner identity; require local confirmation before remote restart. Keep existing database/private-unit ceilings unchanged. Sources: [database migrations](../../mentat_db.py), [backup/restore](../../data_backup_restore.py), [owner validation/sanitization](../../owner_auth.py).

## Enrollment and recovery

1. CLI preflight validates the fixed provider, canonical domain/origin, exact callback and secret-source presence without printing the secret. It explains Google Cloud project, consent screen, web-client creation and callback registration. Setup of these resources remains an operator action; do not create cloud resources silently.
2. Open a ten-minute, single-use enrollment intent accessible only through host administration, while ordinary login remains unable to claim ownership. A controlled setup listener may serve only the authentication ceremony; it must expose no dashboard/data routes. Bootstrap access is separately authorized from ordinary public login.
3. The operator completes Google authentication in a browser using a short-lived enrollment grant. Python verifies the result and stores a pending candidate. The host CLI displays enough verified identity for the operator to check the account, then requires exact candidate/revision confirmation. Only this confirmation activates ownership. Concurrent candidates cannot overwrite each other. Merely visiting the deployment first never claims it.
4. Prepare recovery material through the existing Argon2id capability. Host-admin recovery requires stopped normal serving, exact preview/confirmation, replacement-account proof, and transactional generation change. Revoke every old session, transaction, credential-login route and prior recovery generation. Keep recovery codes off public recovery endpoints in the first Google profile; a code alone must not authorize browser account replacement.

Google's web-server setup requires a web client and registered redirects. Production readiness additionally depends on the operator's app configuration, domain ownership, branding and applicable verification policy. CLI guidance must not promise a universally frictionless or verification-free deployment. Use separate test and production clients/projects; adding Calendar later may change required scopes and verification. [Web-server OAuth setup](https://developers.google.com/identity/protocols/oauth2/web-server), [Google production policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).

## Login transaction and gateway contract

Start login from an explicit same-origin action. Python reserves a five-minute transaction containing digests of random state, nonce and browser-binding values, exact purpose, configuration revision and optional current session revision. Keep the S256 verifier only in bounded process-private memory; restart cancels the transaction and the user starts again. Reuse the aggregate 32/five ceremony ceilings across mechanisms, rather than permitting a second independent allowance. Claim the callback exactly once before external exchange; network ambiguity ends that attempt without replaying its code.

Use a short-lived `Secure; HttpOnly; SameSite=Lax; Path=/` host-only pre-authentication cookie to bind the top-level callback to the initiating browser. The callback is the single fixed GET path permitted to arrive cross-site, with exact configured Host/origin, bounded query fields, no duplicate security parameters and no arbitrary return URL. It exchanges no tokens in browser JavaScript. Give callback responses `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, no third-party resources, and redirect immediately to a fixed clean path. Redact callback queries at Caddy, Node, Python and tracing/error boundaries.

Python exchanges the code at the fixed Google token endpoint with the secret and verifier. Request only `openid email`, omit offline access and profile scope, never persist returned access/refresh/ID tokens, and never hand them to a Calendar adapter. Verify the ID token cryptographically with the pinned Python Google-auth dependency already present, behind an adapter that enforces nonce, owner comparison and bounded transport itself. Do not assume the library validates every application-specific constraint. [Existing requirements](../../requirements.txt), [Google backend validation guidance](https://developers.google.com/identity/sign-in/web/backend-auth).

Proposed transport ceilings: 16 KiB callback query and ID token, 64 KiB token response, 256 KiB key-set response, 16 keys; two concurrent exchanges, three-second connect timeout and ten-second overall deadline per exchange. Fixed HTTPS endpoints only, no redirects or caller-selected discovery/JWKS URL. Validate metadata against an allowlist and cache keys according to bounded expiry; permit one rate-limited refresh for unknown key IDs, then fail closed. No attacker-selected `jku`, `x5u`, algorithm or key fetch. These values need boundary tests, not automatic increases on oversized provider responses.

On exact owner match, atomically issue a fresh 256-bit opaque Mentat cookie and CSRF secret using existing digest storage, bound to the current generation. Keep `__Host-mentat` Secure, HttpOnly, Path=/ with no Domain and explicit SameSite policy. Never store tokens in localStorage or URLs. Every protected route, attachment download and SSE reconnect revalidates the session through named Python capabilities. Session revocation must actively terminate existing streams, not merely delete their reservation rows. Ordinary unsafe requests retain same-origin/CSRF checks; callback admission is not a global exception.

Keep sensitive account changes in host CLI initially. Returning from Google's account picker is not proof of fresh credential entry or MFA; do not mark an OIDC session freshly reauthenticated merely because it is newly issued. Google optional authentication-time/method claims require explicit support. The current passkey reauthentication contract cannot be silently weakened. [Google ID-token claims](https://developers.google.com/identity/openid-connect/openid-connect).

## Threat-driven acceptance matrix

| Threat or failure | Required test/evidence |
| --- | --- |
| First visitor claims instance / wrong Google account | Public login cannot enroll; wrong subject rejected even with matching email; two candidate confirmations race safely. |
| Login CSRF / code injection / replay | Wrong/missing browser cookie, state, nonce, verifier, duplicate callback and concurrent replay all fail without issuing a session. |
| Token substitution | Wrong issuer/audience/authorized party, expired/future token, unsupported algorithm, missing nonce, invalid signature and unknown key fail closed. |
| SSRF and resource exhaustion | Redirecting endpoints, hostile discovery/key URLs, oversized/slow replies, key floods and ceremony floods respect fixed limits. |
| Proxy or route bypass | Forged forwarded headers, wrong Host/SNI, direct backend access, unknown paths, static payload leaks and method variants cannot bypass owner checks. |
| Session theft/reuse | Rotation at login, idle/absolute expiry, generation changes, sign-out and revoked-session SSE closure tested on active streams and reconnects. |
| False step-up | Account picker alone never unlocks owner-reauth operations; those operations remain CLI-only until separately qualified. |
| Secret leakage | Synthetic marker secrets absent from logs, diagnostics, URLs after callback, backups, bridge payloads, browser state and agent child environments. |
| Migration/restore rollback | Passkey roots remain usable before conversion; failed conversion atomic; foreign-key validation passes; old snapshots cannot silently reactivate old owner access. |
| Borrowed browser / provider outage | Login without prior device enrollment; explicit sign-out invalidates Mentat session; outage yields bounded error without local fallback or new account enrollment. |

## Implementation-sized sequence

1. **Authority migration and CLI intents:** implement method/principal/session schema, enrollment/recovery candidate confirmation, aggregate budgets and backup/restore. Keep all public remote serving disabled. Test real legacy schema fixtures and concurrency.
2. **Python OIDC adapter:** fixed transport, token verification, transaction lifecycle and secret isolation; use deterministic fake Google endpoints behind process-private test seams. No generic provider proxy.
3. **Authenticated gateway test profile:** manifest-complete login/callback/logout/session routes and protected data/artifact/SSE admission, tested with disposable HTTPS loopback Caddy. Preserve existing local mode parity. Prove revocation on live streams.
4. **Linux activation and real-provider acceptance:** guided setup, maintenance/start/stop/rollback, domain/TLS/proxy evidence, real Google login from enrolled and borrowed browsers, wrong-account rejection and host recovery rehearsal. Production requires actual operator credentials/domain and cannot be declared complete from mocks.

Resolved direction: Google first, one explicit owner, code + S256/state/nonce, Python token authority, separate integration consent, session-based browser access, CLI account recovery and staged Linux activation. Remaining implementation decisions are exact migration DDL, transport-library adaptation, production domain/service configuration and measured rate-limit usability. None warrants inventing provider credentials or skipping a security gate. Research resolves the design question; it does not complete these implementation slices.
