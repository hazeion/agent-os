# Owner Project planning-input editor

Status: implemented and independently reviewed for the owner-facing part of Project planning-input preparation, after schema 39. It follows the reviewed proposal boundary at `reviews/2026-09-29-project-lead-proposals.md`. Saving an input does not authorize or dispatch a proposal Run.

The Projects & Tasks owner panel reads one exact live Project incarnation, current Project revision, selected lead role version, canonical Agent identity/binding, current Project context version and active grant. If the role is unready or stale, the panel may show historical saved inputs but offers no Save action. The owner types a bounded instruction brief and selects up to eight current-context files in a fixed order, including at most one image. Each selection is verified from the owner-private blob boundary before publication. No path, arbitrary upload, old context file, registered output, URL, runtime reference or provider setting is a selectable input in this slice.

An ordinary active Project metadata edit does not revoke a lead role; role validity follows Project incarnation/status and exact Agent, context, and grant. The new input saves against the current Project revision, while any previously saved input is stale for later proposal admission when that revision changes. The browser sees only an opaque HMAC Project-scope token derived from the private owner epoch, Project ID and incarnation, not the private incarnation itself. This token stays stable across metadata, context and lead edits but changes on deletion/recreation or restore. A local draft is keyed to it; a scope mismatch blocks Save and requires an explicit owner rebase onto the new Project/context/lead before any old text can be used.

An exact save request includes Project ID/revision, lead role ID/revision, current context ID and grant revision, expected input revision, a private HMAC selection token, a 128-bit client action ID, instructions and ordered attachment IDs. Schema 40 adds one bounded immutable action receipt for each saved version. Python first looks up the action ID, validates its exact request digest and retained input version, and returns that historical committed result even if current Project/role/grant/head state has changed; the response labels it historical or stale rather than current. A reused action ID with changed body conflicts. For a new ID, Python revalidates Project/role/Agent/context/grant/file bytes in one private lock and guarded SQLite transaction, inserts one immutable schema-39 version, its frozen file metadata and the action receipt together, validates the prospective full backup graph, then commits. A changed identity, grant, context, Project revision, file, or input head fails closed. The token is derived from a private owner epoch and exact current authority snapshot; it never grants execution. A lost response is reconciled by the exact action receipt; no automatic new request is sent.

Schema-40 migration backfills explicit legacy receipts for any pre-editor schema-39 rows, using a deterministic non-client action ID and their retained file digest. A sealed legacy-ID table and migration cutoff distinguish those rows from later owner Saves. New owner receipts retain the two exact opaque selection tokens, allowing backup validation to recompute the request digest, including its action ID, from the immutable input version and ordered file IDs. Every schema-40 input has exactly one receipt; missing receipts, changed valid-hex digests, changed action IDs and owner-to-legacy relabeling fail backup validation. Legacy receipts do not imply that an owner Save occurred.

The owner website uses a fixed same-origin session/CSRF route and an exact bounded Node-to-Python bridge capability. The browser sees safe Project/Agent/context names, selected file names/types/sizes/availability, revision and stale reasons; it never sees blob keys, content digests, local paths, runtime bindings or credentials. The draft remains local across Project navigation and failed/uncertain saves only while its Project-scope token matches. During an uncertain save it retains the same action ID and exact request body across unmount/navigation; it mints another ID only for an intentional new save after reconciliation. The UI shows the 32-version-per-incarnation limit and fails closed at capacity. Reference-aware pruning or replacement must be reviewed before qualified proposal execution becomes available. UI copy states that a saved Project input is preparation only and that lead proposals are unavailable until the separate qualified proposal-only Run slice passes.

Tests cover selection before context, revoke/regrant and explicit lead reselection, changed context pointer, Agent replacement, Project deletion/recreation, file expiry or digest mismatch, 8-file/1-image limits, two-device competing writes, exact action replay and lost-response receipt reconciliation, full 32-per-Project-incarnation and 256-global capacity, private-backup tampering and restore, schema-5 export, fixed owner-session/CSRF route, bounded safe browser projection, and zero Run/adapter effects.
