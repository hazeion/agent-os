# Official Hermes Project execution: proposed controller amendment

Status: **design for owner decision, not execution authority**. This assesses the installed, unchanged official Hermes `v2026.9.24` / `0.21.5` checkout at commit `f97608f178d1ffeca59860195ab7da295f7c8e5f`. No model call, upstream edit, Hermes configuration edit, Kanban mutation, or private-data read was made for this assessment. The current [worker admission contract](2026-09-29-project-worker-admission.md), [architecture](../ARCHITECTURE.md), [implementation plan](../IMPLEMENTATION_PLAN.md), and issues [#239](https://github.com/hazeion/agent-os/issues/239) and [#262](https://github.com/hazeion/agent-os/issues/262) remain the safety floor.

## Decision

**Recommend a narrow architecture amendment:** Mentat owns the durable, capability-scoped Project worker controller and admission receipt. The official Hermes Agent loop runs as its isolated, one-shot runtime adapter. Hermes Kanban remains the only durable **delegation board** and the only Hermes Task mutation surface, through fixed supported CLI/API calls and exact preview, confirmation and readback. A Kanban card is not treated as a verified worker lease or as a substitute for a canonical Mentat Run. Agent Console Turns are never a scheduler. Existing Console and other runtime adapters retain their present contracts.

This changes one sentence of the proposed worker contract: Hermes itself need not provide a single atomic `create prepared worker` operation when Mentat's controller owns execution. The alternative is to retain that Hermes-owned admission requirement and wait for an upstream supported worker API. Stock `0.21.5` does not expose it. The owner has already chosen official Hermes with no fork fallback; this specific controller-versus-Hermes-dispatcher ownership choice should be recorded before enabling Project Runs. All isolation, exact input, budget, Stop, output, approval and recovery guarantees remain mandatory.

## Phase 1: proposal-only Project Run, no Kanban card

Before proposal reservation, enforce one shared, durable **canonical Agent/runtime-binding capacity** check across Console, Task and every Project source. An unqualified adapter keeps its existing ceiling of one compatible active Run; a larger or partitioned ceiling requires separate exact scope-specific qualification and a bound capacity receipt. One unresolved proposal per Project does not protect an Agent who leads multiple Projects or is already serving a Console Run. No additional private scheduler or Hermes profile can create an extra slot.

Start with the existing schema-42 Project proposal receipt and schema-41 `project_proposal` Run guard. A lead proposal is Project-scoped preparation, not a Hermes Task delegation; it needs no synthetic Kanban card. Under Mentat's private lock and one SQLite transaction, revalidate the live Project incarnation/revision, current context pointer, lead/Agent/binding/grant, immutable planning input and each selected byte, exact owner authorization, one unresolved proposal generation, operations and finite attempt/wall/work reservation. Commit the canonical `project_proposal` Run and Project Run-input receipt together **before** external execution. Lift the database no-dispatch guard only in the reviewed admission migration after Run attention, Inbox, backup/retention and output provenance accept this source. No browser flag may choose the executable, runtime method, input path, provider, model, toolset or endpoint.

A durable Mentat controller claims only that exact reserved Run by compare-and-swap, records generation, process-scope identity and broker capability, then launches a fixed official one-shot command with an allowlisted environment and server-owned `--query-file`. It uses a fresh synthetic `HERMES_HOME`, no owner `.hermes` or credential files, and an isolated official checkout/venv mounted read-only. Mount only the eight selected read-only input snapshots (at most one image), a bounded run-owned output directory and the required runtime libraries. No unrelated home, WSL Windows mount, Docker socket, Kanban database or arbitrary workspace is visible. The entire Agent loop and descendants must be in one tested Linux scope with a hard parent watchdog and descriptor-relative no-follow cleanup. `--safe-mode` and a narrow toolset are additional controls, not the boundary; if a controlled provider plugin is needed, put only that reviewed code in the synthetic home and verify the exact loaded inventory. For the first proposal, disable subagents, generic shell, browser, MCP, hooks and arbitrary skills, and permit only reading selected context and returning one bounded JSON proposal.

The worker must reach **only** a per-Run inference broker, never the provider directly. A candidate is a local OpenAI-compatible endpoint selected by a fixed stock provider profile or controlled plugin. Since an `--unshare-net` worker cannot reach a host loopback endpoint automatically, qualification must prove a concrete namespace-local bridge (for example an inherited Unix socket plus a small namespace-local HTTP front end) and the stock client transport. The worker receives no provider key; the broker enforces the exact runtime revision. **Credential custody stays with Hermes or an explicitly reviewed operator credential boundary:** a trusted host-side Hermes process may resolve credentials through its supported provider/auth interface, or the operator may provision a credential reference through an existing protected secret source. Mentat's controller and broker must not directly open, parse, copy, cache or shadow Hermes `.env`, `config.yaml`, provider stores or token files to make this work. A host-side Hermes `ctx.llm` or provider plugin is only a candidate seam until its resolution, identity and call behavior are verified on stock source; if no supported resolution/transport exists, production admission remains closed. If official `--safe-mode` removes the required provider route, choose a synthetic-home allowlisted plugin only after verifying it cannot initialize other tools or connect elsewhere. Neither a provider profile nor `ctx.llm` by name proves credential isolation or broker qualification.

The broker durably journals one call identity and request digest **before** each provider submission. At most one unresolved call exists per Run. Hermes/SDK retries with the same or a different body cannot cause a second provider request while the first outcome is unknown; the broker returns the recorded result or an unresolved failure, then fences further calls until supported reconciliation. Every accepted call consumes the Run's finite request/output-token/work reservation. Define and test the actual work unit and conservative model-specific request maxima; usage estimates alone cannot promise a hard money cap. A timeout or crash retains the canonical Run and inputs as checking/unknown with no automatic resubmission.

The controller accepts only the one terminal `result` with exit success and verified nonpartial completion from the owned process/scope. It copies bounded final JSON text into its own immutable registered export/blob using trusted descriptors, freezes digest and producing Run evidence, then invokes the existing pure proposal parser. Missing, extra, malformed, partial or late output becomes quarantined recovery evidence, never an Apply candidate. Proposal receipt/intake, owner diff/Apply and later Task plan approval remain separate exact operations.

## Phase 2: approved Task Runs and Hermes Kanban delegation

Task admission uses the same Agent/runtime-binding capacity reservation before any Kanban create or worker launch, counting Console, other Task and Project Runs together. Recheck it for deferred checkpoints and explicit owner retries; a blocked Kanban card, separate control root or different Project never grants a second slot.

Keep the existing Hermes Kanban adapter's exact preview/confirmation/readback. After an owner-approved format-2 plan and checkpoint, reserve the canonical Task Run, immutable Task Run-input receipt, budget and idempotent action receipt under the Mentat lock. Use one immutable Kanban card reference **per canonical execution attempt** so a revision never takes over an earlier card. The controller uses a **fixed** Kanban create operation for that card on a dedicated, pinned, owner-private `HERMES_KANBAN_HOME` **root**, parked at `blocked` with `--max-retries 1` and a safe opaque Mentat reference; no private context, credential, local path or prompt goes into card prose. Stock [`kanban_home()`](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/hermes_cli/kanban_db.py#L399) deliberately shares the default root across profiles, and the gateway [enumerates every live board in its selected root](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/gateway/kanban_watchers_common.py#L37). A different profile or board in the default root therefore provides **no dispatch isolation**.

Python fixes the control root in private configuration and passes it only in the allowlisted environment of named Kanban adapter calls. The browser cannot choose a root, board, profile or command. The root must be descriptor-pinned, no-follow, owner-private and disjoint from every ordinary Hermes gateway/dispatcher root; no gateway or standalone Kanban daemon may run against it. Bootstrap that root/board only through a separately reviewed **fixed supported Hermes CLI/API operation** (for example exact `kanban init`/board creation under the fixed environment) with preview, confirmation and readback; never create Hermes storage tables or write a Hermes config file directly. A separate control profile is optional, not the root-isolation mechanism. If a defense-in-depth dispatch setting is used, change it only through a separately approved supported operation with exact readback, never by editing `config.yaml` or toggling the owner's global ordinary dispatcher. Qualification checks the actual live gateway environment/root and confirms the ordinary default root, boards and dispatcher are unchanged, then fails closed if root separation or service state cannot be proved. Keep the card unassigned, with no control-root default assignee; the canonical Mentat Task/Run receipt records the actual selected Agent. These are further defenses if a card is accidentally made ready, not substitutes for root isolation. The control-root card is a delegation ledger; Mentat's canonical Run is the truthful execution state. Do not claim that a blocked Hermes card is running, and do not use `kanban claim` as a verified Mentat worker lease. The UI must explain the distinction. The paired control-root state and Mentat references need an exact backup/restore/reconciliation contract; a restore missing either side cannot silently revive execution authority.

The new adapter must compare every safe card field and its exact Project/Task/Agent intent on readback before launching work. Stock `create` is not an exact digest-bound operation, and its list/show JSON omits the key. Therefore a lost create response must leave the Mentat operation unknown unless a **separately reviewed read-only** pinned-schema lookup proves the unique key and full card state, or a bounded high-entropy marker in a returned field has been proved unique by an exact scoped scan. Never submit `create` again to answer uncertainty. A changed-body/same-key readback is conflict. Even if Hermes creation succeeded, no Agent executes until the card and Mentat reservation reconcile exactly. Any new read-only lookup must not write, shadow or synchronize Hermes core files.

Once the card is verified, launch the same qualified isolated official worker under the Task's exact approved operation set. A public-research Run gets no private Project files or notes; only the owner-reviewed public brief, a separate fixed HTTPS/443 public broker with pinned public DNS/IP and bounded redirects/bytes/time, and the inference broker. Private synthesis has selected files and no public-web capability. Results are registered immutable generated-output versions with exact producer Run/Task incarnation and approved plan node/slot, not relabeled owner edits or generic attachments. A successful Run produces an owner Inbox review item; the Hermes card can remain parked with a bounded status comment until the owner accepts. Only an exact owner acceptance/confirmation may complete the blocked card through supported Kanban mutation and readback; a revision request creates a new canonical Run/reservation, never an automatic Hermes requeue. Approved handoffs reserve each successor from current grants, checkpoint and registered output versions. Manual owner assignment remains available.

The current Kanban dispatcher, ordinary Hermes Agent profiles and interactive Console continue operating as before on their original shared root. Mentat-scoped cards remain in the separate non-dispatching control root. Any unexpected card change, including ready, running, done, archived, assignment, body or dependency mutation, is a conflict/recovery event, not authority to execute or accept work. The controller never edits `kanban.db` or any other Hermes core file; supported fixed calls handle all Kanban mutations.

## Crash, Stop, and acceptance gates

The controller is a durable local service, not an in-memory request handler. Its claim/lease generations, immutable admission and budget-debit receipts, broker call identities/request digests/outcomes, capability revocations and output pins belong to the **validated owner-private Console backup/restore consistency unit** with the canonical Run, receipt and Event graph. They cannot live only in process memory, an unvalidated sidecar or a disposable broker cache. Backup validates their foreign keys, monotonic budget accounting and bounded retention; restore changes the authority epoch and fences every pre-restore live process scope, broker capability and delayed output before any new reservation. It never resets a spent budget, replays an unresolved provider request or lets restored stale grants authorize a Run. On restart it reconciles Mentat Run/receipt/action evidence, exact OS scope, broker call journal and Kanban card/readback. A still-live scope remains active/checking; a missing or ambiguous scope remains unknown until evidence supports interruption. It never starts a second worker for an unresolved generation. Stop revokes broker inference/research capability and kills/verifies the entire generation's process scope. It reports local termination separately from an already-submitted external provider call, which may remain unknown. A completed output can cross to review only after exact terminal Run evidence and blob readback; owner acceptance cannot be inferred from Hermes card completion.

Before advertising `project_proposal` or approved Task execution, test the exact built official release on the actual Linux host: source/venv pin; synthetic-home/plugin and tool inventory; selected input/read-only and unrelated-path denial; no host or Windows mounts; secret-free provider bridge; public-broker SSRF defenses; output-only write boundary; concurrent/changed-body admission; lost Hermes create and provider responses; separate Kanban-root/gateway enumeration, supported bootstrap and paired backup/restore; broker duplicate retry; private-unit call/budget graph validation; restore-epoch fencing without replay or budget reset; finite work/attempt/wall budget; nested children/tool escapes; crash/restart/restore; revocation; Stop/descendant and late-provider behavior; Run/Inbox/backup/retention; and owner review. Use two independent code reviews per slice, local and hosted tests, built desktop/mobile acceptance, then one operator-configured live provider/garage walkthrough with secret-free evidence. Until each gate passes, keep controls unavailable and the schema-41 proposal insert guard in force.

Qualification must include cross-source races: two Projects reserving the same lead Agent, proposal versus active Console, Task versus proposal, checkpoint release versus Stop, and retry after revocation or restore. Prove the unqualified ceiling of one and only widen it after exact binding-specific capacity evidence.

## Scope decision the owner should make

Approve or reject **Mentat-owned isolated Project worker execution around unchanged official Hermes, with Hermes Kanban as the durable delegation ledger rather than the worker dispatcher for Mentat-scoped cards**. This is the only architectural authority change proposed here. It preserves manual assignment and all exact owner approval, safety and review boundaries. If the owner wants Hermes itself to atomically own Project worker admission/claims, a new upstream supported operation is needed; none of Run API idempotency, Subagent Lifecycle, plugin middleware, `ctx.llm`, or ordinary Kanban create/dispatch provides that contract in stock 0.21.5. Selecting the controller route authorizes implementation and qualification work, **not** production Agent dispatch before those tests pass.

## Review evidence

Two independent source/contract reviews found control-root isolation,
credential custody, supported bootstrap, backup/restore fencing and shared
cross-source capacity gaps. All were corrected; both final re-reviews are clear.
The controller amendment awaits the owner decision. No model invocation,
runtime dispatch, Hermes storage mutation or execution-guard change forms part
of this design slice.
